# 授权门禁 · 完整说明（使用 / 签发 / 维护 / 排错）

> 适用版本：**v1.3.2 及以后**（含授权门禁的版本）
> 最后更新：2026-10-19
> 读者：① 使用本软件的人 ② 负责签发证书的人 ③ 维护本仓库的人（含 AI 助手）

## 0. 一分钟速览

```
你拿到一个 totoro-heaven.exe
  → 双击运行（浏览器自动打开）
  → 因为没有授权，页面会停在「授权」页
  → 把那台机器的「机器码」发给签发者
  → 拿到「授权证书」（一长串字符）
  → 粘回「授权」页 → 点「激活」
  → 完成，之后可离线使用 365 天
```

**谁是签发者**：持有私钥 `tools/keys/license-private.pem` 的那个人。**只有他能发证书。**

## 1. 名词对照（先统一说法，避免沟通误解）

| 名词 | 含义 | 谁会产生 |
| --- | --- | --- |
| **机器码** | 这台机器这个安装的唯一指纹，形如 `A76A-1BA9-553D-BB21` | 程序自动生成（首次运行） |
| **授权证书** | 一长串字符（`eyJ2...` 开头、中间一个点、后面一段签名） | **签发者**用私钥签出 |
| **私钥** | `tools/keys/license-private.pem`，签发凭据 | 签发者本机，**唯一一份** |
| **公钥** | 已内置在程序里（`server/utils/license/publicKey.ts`） | 随程序分发，**公开也无所谓** |
| **激活** | 把证书粘进程序并保存到本机 | 使用者操作 |
| **解绑** | 删除本机的授权文件 | 使用者操作 |

> ⚠️ 常见误解：
> - 「key」= 机器码（**不是**秘密，可以随便发）
> - 「激活码」= 授权证书（**是**签发产物，别和机器码搞混）
> - 证书**不能**通用 —— 一张证书只对一台机器有效

## 2. 使用者：怎么激活

### 2.1 启动

1. 双击 `totoro-heaven.exe`
2. **可能弹 SmartScreen 蓝色警告**（因为程序没买代码签名证书，必然出现，不是病毒）
   → 点「**更多信息**」→ 「**仍要运行**」
3. 浏览器会自动打开 `http://localhost:3000`
4. 因为未授权，**页面会自动跳到「授权」页**（这是正常的）

> 如果窗口一闪而过、程序没起来 → 跳到 §8 排错手册

### 2.2 取机器码

在「授权」页的「**本机机器码**」卡片里，形如：

```
A76A-1BA9-553D-BB21
```

点「复制机器码」按钮，把这一串发给签发者。

### 2.3 激活

1. 签发者回给你一段**很长的字符**（`eyJ2...` 开头）
2. 整段粘进「粘贴授权证书」的输入框
3. 点「**激活**」
4. 成功后显示：授权对象、剩余天数、到期时间；顶栏变成「已授权 · N 天」

> **粘贴容错**：换行、空格、多余的空行都会被自动忽略，不用手工整理。
> **失败时**会明确告诉原因（格式错 / 签名无效 / 机器码不匹配 / 已过期），照着改就行。

### 2.4 之后

- **可以离线使用**，不需要联网验证
- 到期前联系签发者续期（重新拿一张证书粘进来）
- 换机器 / 重装系统 → 机器码会变 → 需要重新签发

## 3. 签发者：怎么发证书

### 3.1 前置条件

你手上必须有私钥：

```
<仓库根>\tools\keys\license-private.pem
```

**这个文件不在仓库里**（已被 `.gitignore` 排除），只在签发者本机。

如果它不存在、而你确定没有别处备份 → 说明密钥对从未生成或已丢失，见 §4 红线 1。

### 3.2 签发

**方式 A：图形界面签发器（推荐，不熟悉命令行的用这个）**

双击 `license-issuer.exe` → 浏览器自动打开表单 → 填「机器码 / 授权对象 / 有效天数」→
点「签发授权证书」→ 一键复制激活码。

交付给签发者时，**两个文件要放在同一个文件夹**：

| 文件 | 说明 |
| --- | --- |
| `license-issuer.exe` | 签发工具（约 88 MB，自带运行时，**不需要装 Node**） |
| `license-private.pem` | 私钥（**没有内置进 EXE**，必须单独放） |

工具会按顺序在这些位置找私钥：
`exe 同目录` → `exe 同目录\keys\` → `%LOCALAPPDATA%\totoro-heaven` → `用户主目录`。

> ⚠️ **一定要看页面的「自检」结果**（这是最容易翻车的地方）：
> - ✅ **自检通过** ⇒ 这张证书对方一定能激活，可以发；
> - ❌ **验不过** ⇒ 说明这把私钥与程序内置公钥不是一对，**这张证书发了也没用** ——
>   先找开发者核对密钥，别急着发出去。
>
> 现实中真出现过：拿错私钥签了一堆证书，用户一个都激活不了，还得挨个重发。

**方式 B：命令行（开发者 / 批量场景）**

```powershell
cd <仓库根>
node tools/license-issue.ts --machine "对方发来的机器码" --sub "对方的名字" --days 365
```

输出会打印一段「**把下面这一整段发给用户**」的字符 —— 原样发给对方即可。

### 3.3 参数表

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `--machine` | ✅ | 对方发来的机器码。**让对方直接复制**，别手抄；大小写与连字符会自动归一 |
| `--sub` | ✅ | 授权对象（显示在对方的「授权」页上），填人名/备注 |
| `--days` | | 有效天数，默认 **365**；到期后还有 **半天（12 小时）离线宽限** |
| `--features` | | 功能位，默认 `pro`（当前仅记录，不做功能限制） |
| `--lic` | | 许可证编号，默认自动生成 `TH-XXXX-XXXX` |

### 3.4 签发台账

每签一张都会追加一行到：

```
<仓库根>\tools\keys\issued.jsonl
```

内容含：时间 / 编号 / 授权对象 / 机器码 / 证书。用于对账与重发。
该目录同样不入库（含客户信息）。

### 3.5 首次生成密钥对（**只在项目还没有密钥对时做**）

```powershell
node tools/license-keygen.ts
```

会生成私钥，并自动把公钥写进 `server/utils/license/publicKey.ts`。

> 🔴 **如果项目已经有公钥，绝对不要执行这条命令**，原因见 §4 红线 1。

### 3.6 卡密与在线激活（**自动发货**用这个）

如果要做到「买家付款后立刻自动发货」，靠手动签证书**做不到** —— 因为证书绑机器码，
而机器码要等买家运行程序才知道。

解决办法是 **卡密 + 在线激活**：

```
① 付款成单   → 店铺自动发一张「卡密」（TH-XXXX-XXXX，一次性）
② 买家激活   → 程序里输入卡密，程序带着本机机器码请求激活服务
③ 服务端     → 验卡密未用过 → 用私钥**现签**一张绑定该机器的证书 → 返回
④ 程序       → 本地验签通过 → 落盘 → 激活完成（之后完全离线）
```

- **服务端代码与部署**：见 [`tools/activation-server/README.md`](../tools/activation-server/README.md)
  （零依赖单文件，任意 Node 18+ 服务器可跑；国内建议用国内云服务器，别用境外免费服务）
- **发卡命令**（一次一批）：

  ```bash
  curl -X POST https://<你的激活服务>/admin/cards \
    -H "Authorization: Bearer <ADMIN_TOKEN>" \
    -H "Content-Type: application/json" \
    -d '{"count":50,"days":365,"sub":"闲鱼订单"}'
  ```

- **让程序连上服务**：改 `server/utils/license/activation.ts` 里的 `ACTIVATION_URL_BUILTIN`
  后重新打包；或在数据目录放一个 `activation-url.txt`（内容只有一行 URL）临时指定，**不用重新打包**。

> ⚠️ **私钥会放到服务器上** —— 这是在线激活的固有代价：能自动签发的机器必然持有私钥。
> 服务器安全要求：只跑这个服务、私钥 `chmod 600`、管理密钥 ≥24 位随机、走 HTTPS、
> 定期备份 `cards.json`（丢了已用卡记录 = 卡密可被重复使用）。

## 4. 🔴 十条红线（做了就会出事故）

> 这一节是给**所有维护者（包括 AI 助手）**的硬约束。每条都附了"为什么"。

### 红线 1：不要重新生成密钥对

```powershell
node tools/license-keygen.ts        # ← 除非项目里还没有公钥，否则禁止
node tools/license-keygen.ts --force # ← 永远禁止
```

**为什么**：重新生成会换掉公钥。程序里内置的是旧公钥 ⇒ **所有已发出的证书立刻全部作废**，
每个用户都得重新拿证书。而且换公钥必须重新打包 EXE 才能生效，中途会造成版本错乱。

### 红线 2：不要把私钥提交、上传、发群

```
tools/keys/license-private.pem   ← 只留在签发者本机
```

**为什么**：私钥 = 签发权。泄漏后任何人都能造证书，整套门禁归零。
`.gitignore` 已屏蔽 `/tools/keys/`，但**不要**用 `git add -f` 绕过它。

> 需要让第二个人能签发时：**私下传文件**（微信/QQ/U 盘），并接受"任一方泄漏即全泄漏"的代价。

### 红线 3：不要改变机器码的算法或实例 ID 的存放规则

涉及：`server/utils/license/instance.ts` 的
- `FINGERPRINT_SALT`
- `INSTANCE_ID_NAME` / `LICENSE_FILE_NAME`
- `LICENSE_DIR_CANDIDATES` 的**读取顺序**

**为什么**：机器码是由「实例 ID + 平台 + 架构」哈希出来的。
一旦换 salt、换文件名、或让程序**读不到**原来的 `instance-id`，机器码就变了 ⇒
**所有已发出证书全部对不上**。

> 允许改的：**写入**的回退顺序（新增候选目录没问题）。
> 不允许改的：**查找已有 `instance-id` 的顺序**（必须从原来的位置优先找）。

### 红线 4：不要把运行目录 / 数据目录写死成单一路径

涉及：`pack/sea/launcher.mjs` 的 `RUNTIME_DIR_CANDIDATES`、
`server/utils/license/instance.ts` 的 `LICENSE_DIR_CANDIDATES`。

**为什么**：实测过故障 —— 有些机器上 `%TEMP%` 和 `%LOCALAPPDATA%` **都不可写**
（杀软过滤驱动 / Windows 受控文件夹访问 / 企业策略 / 沙箱），
写死单一路径会导致：① 程序启动就崩（窗口一闪而过）② 永远激活不了。

**必须保留**：先探测可写性（写探针文件），写不进去就换下一个候选。

### 红线 5：不要把校验只放在前端

**为什么**：前端只是 UI。真正值钱的能力都在 `/api/**` 后面（读数据、代提交）。
只藏按钮的话，用户按 F12 或直接 `curl` 就绕过了。

**必须**：服务端中间件 `server/middleware/license.ts` 拦截 `/api/**`（仅放行授权自身接口）。

### 红线 6：证书校验失败时，**绝不**放行

**为什么**：`verifyCertificate()` 的每一种失败（签名无效 / 机器码不符 / 过期 / 公钥未配置）
都必须返回 `ok: false`。**尤其**"公钥为空"时不能当成"不校验" —— 那是静默失效，
不报错、发现不了，等于门禁不存在。

**判据**：`publicKey.ts` 为空 ⇒ 拒绝一切（fail closed）。

### 红线 7：不要把"厂商解包产物 / 源码逐行抄"的痕迹加回来

涉及：`utils/mp/**`、`src/mp/**` 里源码注释的措辞。

**为什么**：历史上代码里写过"与小程序端逐行等价实现""从厂商解包产物提取"这类自述，
构成**书面自证**的合规风险（详见仓库根目录 `NOTICE`）。
现在统一改成「按接口契约 / 按实测行为确认」的口径 —— **不要再写回去**。

> 原始来源记录集中在 `NOTICE` 里，这是"记录完整且不散落"的做法，不是隐藏。

### 红线 8：不要跳过 `npm run verify`

**为什么**：这个仓库的 CI 跑的就是它（单测 + 3 个 typecheck + 接线契约 + 检查器自测）。
跳过会导致"本地看着没问题、推上去 CI 红"。

```powershell
npm run verify
```

### 红线 9：改 `package.json` 后必须同步 `package-lock.json`

**为什么**：CI 用 `npm ci`，它要求两者**严格一致**，不一致直接失败且**后面的测试一步都不跑**。
历史事故：某次"重新解析锁文件"漏了 `@parcel/watcher`，导致 CI 连红 5 次。

```powershell
npm install --package-lock-only   # 只更新锁文件，不动 node_modules
```

### 红线 10：发给使用者的只有 `.exe` 这一个文件

```
✅ 发：dist\totoro-heaven.exe
❌ 不发：整个 dist 文件夹（含构建缓存 sea/）
❌ 不发：dist\runtime（程序本体，会重建）
❌ 不发：dist\totoro-heaven-data（授权数据，含激活记录）
```

## 5. 架构：文件与数据流

```
【软件内置（随 EXE 分发）】
  server/utils/license/publicKey.ts       公钥（Ed25519 SPKI PEM）
  server/utils/license/certificate.ts     证书编码/解析/验签/有效期判定（纯函数）
  server/utils/license/instance.ts        机器码（实例 ID + 平台 + 架构）、多候选目录
  server/utils/license/state.ts           状态读取、激活/解绑、5 分钟缓存
  server/utils/license/gate.ts            闸门路径判定（含路径穿越防护，纯函数）
  server/middleware/license.ts            服务端闸门：未授权 → HTTP 402
  utils/mp/licensePolicy.ts               前端策略：6 个状态分支（纯函数）
  composables/useLicenseState.ts          前端状态缓存（守卫/顶栏/页面共用）
  middleware/license-guard.global.ts      前端路由守卫：未授权 → 跳 /license
  pages/license.vue                       「授权」页 UI
  layouts/default.vue                     顶栏授权状态 chip + 「授权」入口
  pages/version-info.vue / AboutDialog    软件内的授权说明文案

【只在仓库、不进 EXE】
  tools/license-keygen.ts                 生成密钥对（一次性）
  tools/license-issue.ts                  签发证书（命令行，签发者用）
  tools/license-issuer/                   图形签发器（issuer.mjs + build-issuer.mjs → EXE）
  tools/keys/                             私钥 + 签发台账（🔴 gitignore）
  tools/README-授权使用.md                签发侧快速上手
  docs/授权门禁-完整说明.md                 ← 本文件
```

### 激活数据流

```
① 首次运行
   程序读 instance-id（没有就生成）→ 算出机器码 → 显示在「授权」页

② 签发者签发
   issue.ts 用私钥对 {机器码, 对象, 有效期} 签名 → 得到证书字符串

③ 使用者激活
   粘贴证书 → 服务端验签（公钥）→ 校验机器码/有效期 → 写入 license.json

④ 之后每次运行
   读 license.json → 本地验签（约 50 微秒）→ 缓存 5 分钟 → 放行或拦截

⑤ 请求拦截
   未授权：服务端对所有 /api/** 返回 402；前端路由守卫把用户送到「授权」页
```

## 6. 数据存放的三个目录（排错必看）

| 目录 | 内容 | 能删吗 | 说明 |
| --- | --- | --- | --- |
| `%LOCALAPPDATA%\totoro-heaven` | `instance-id`、`license.json` | ⚠️ **删了机器码会变、要重新签发** | 首选位置 |
| `<EXE 旁边>\totoro-heaven-data` | 同上（回退位置） | ⚠️ 同上 | 上面那个不可写时才用 |
| `<EXE 旁边>\runtime` | `server/`、`public/` | ✅ 可删（下次运行自动重建） | 程序本体 |

> **怎么知道我用的哪个？** 「授权」页底部会显示「数据目录：…」，那就是实际位置。

```powershell
cd <仓库根>

# ① 确认代码是好的

# ② 版本页贺图（打包脚本强制检查，缺了会 throw）
```

> ⚠️ 打包前先关掉正在运行的 `totoro-heaven.exe`，否则会报"文件被占用"。

## 8. 排错手册

### 8.1 双击后窗口一闪而过 / 有报错文字

用同目录下的诊断脚本启动，它会**把输出存到 `run.log` 并停住**：

```
双击 dist\start-debug.cmd
```

然后看窗口里的内容。常见报错见下表。

| 报错文字 | 原因 | 处理 |
| --- | --- | --- |
| `EPERM ... totoro-heaven-runtime\app.tar.gz` | `%TEMP%` 不可写 | 已修复（自动回退）。若仍出现，说明用的是**旧版 EXE**，换最新的 |
| `EPERM ... license.json` | `%LOCALAPPDATA%` 不可写 | 已修复（自动回退到 EXE 旁）。同上，换最新 EXE |
| `此 EXE 须以打包后的 SEA 单文件运行` | 文件被截断 / 杀软剥离了数据块 | 核对字节数；加杀软白名单后重新复制 |
| 窗口完全没有、进程也没有 | 被系统/杀软直接杀掉 | 加白名单，或右键「以管理员身份运行」 |

### 8.2 授权页的各种提示

| 提示 | 含义 | 处理 |
| --- | --- | --- |
| 「未激活（请粘贴供应商发给你的授权证书）」 | 正常，还没激活 | 走 §2.3 |
| 「证书格式不正确」 | 复制不完整（漏字/截断） | **整段重新复制** |
| 「证书签名无效」 | 证书被改过，或不是同一把私钥签的 | 找签发者确认 |
| 「证书与本机机器码不匹配」 | 这是发给**另一台机器**的证书 | 用本机机器码重新签发 |
| 「授权已过期」 | 超出离线宽限 | 重新签发 |
| 「本程序尚未配置许可证公钥」 | 打包时公钥为空 | 签发者没跑 keygen，或用了错的源码打包 |
| 「机器码无法持久保存」 | 三个候选目录**都**不可写 | 检查权限/杀软；此时机器码每次都会变，必须先解决 |
| 「开发模式：授权校验已跳过」 | 跑的是 `npm run dev` | 正常；正式版会强制校验 |

### 8.3 顶栏状态的含义

| 显示 | 含义 |
| --- | --- |
| 未授权（黄色） | 未激活 / 证书无效 → 点击直达授权页 |
| 已授权 · N 天（绿色） | 正常 |
| 剩 N 天（黄色） | 距到期 ≤ 7 天，建议续期 |
| 宽限期（黄色） | 已过有效期但仍在**半天**离线宽限内（提示尽快续期） |
| 授权已过期（红色） | 彻底失效，需重新签发 |
| 开发模式（蓝色） | `npm run dev` 下不校验 |

### 8.4 激活成功后又变回未授权

排查顺序：
1. 是不是**换了 Windows 账户**？（`C:\Users\a` → `C:\Users\admin` 机器码会变）
2. 是不是**删了** `%LOCALAPPDATA%\totoro-heaven`？
3. 「授权」页上看「数据目录」指向哪 —— 如果指向临时位置，清理临时文件会丢授权
4. 是不是证书**到期**了？

## 9. 已知限制（如实说明，不要当成 bug 去"修"）

| 限制 | 原因 | 能不能解决 |
| --- | --- | --- |
| 一张证书只对一台机器 | 设计如此（防转发） | 不解决 |
| **无法远程吊销** | 离线模型，没有服务器 | 需要另建在线激活接口才能做 |
| 没有"几台设备"的席位统计 | 同上 | 同上 |
| `features` 功能位只记录不生效 | 目前没有需要分级的功能 | 有需求再做 |
| 签名证书可以"删掉校验代码"绕过 | 程序在用户机器上 | 提高破解成本靠混淆；根治要把核心能力放云端 |
| 无代码签名，首次运行会 SmartScreen 警告 | 没买证书 | 买代码签名证书 |

## 10. 给 AI 助手的硬约束（重要）

> 如果这个仓库由 AI 助手维护，请把这一节作为**不可协商的约束**。

### 10.1 动手前必须做

1. 先读本文件，特别是 **§4 十条红线**。
2. 确认当前版本号、`git status`、以及最近一次 CI 是否绿。
3. 任何涉及 `server/utils/license/**`、`pack/sea/**`、`middleware/**` 的改动，
   先说明"会不会影响机器码 / 已发证书"，再动手。

### 10.2 明确禁止（做了就是破坏性变更）

- ❌ 执行 `node tools/license-keygen.ts`（除非项目里确实没有公钥）
- ❌ 修改 `FINGERPRINT_SALT`、`instance-id` 文件名、或"查找已有 instance-id"的顺序
- ❌ 删除或弱化 `RUNTIME_DIR_CANDIDATES` / `LICENSE_DIR_CANDIDATES` 的可写性探测与回退
- ❌ 把授权校验改成"异常时放行"，或把 `publicKey` 为空当作不校验
- ❌ 把校验只留在前端、或删除 `server/middleware/license.ts`
- ❌ 用 `git add -f` 提交 `tools/keys/`
- ❌ 在源码注释里写"照厂商源码""逐行等价""从解包产物提取"
- ❌ 声称"已验证"却没有真的跑过命令（这个仓库极重视证据）

### 10.3 改完必须做

```powershell
npm run verify          # 单测 + 3 个 typecheck + 接线契约
```

如果改了依赖：

```powershell
npm install --package-lock-only
npm ci --dry-run   # 可选：验证锁文件一致性
```

### 10.4 交付时必须说明

- 改了什么、为什么、影响面（尤其：**会不会让已发证书作废**）
- 验证跑了什么、结果如何（贴真实输出，不要"应该没问题"）
- 有没有未验证的部分（如实列出）

### 10.5 本仓库的既有约定（AI 常踩）

| 约定 | 说明 |
| --- | --- |
| `utils/mp/**` **不是** Nuxt 自动导入范围 | 用它们必须**显式 `import`**；漏了会在**运行时**报 `is not defined`，typecheck 发现不了 |
| 模板注释里不要写 `**加粗**` | 会被 UI 文本检查器拦下（Vue 不渲染 markdown） |
| `server/**` 不得 import 前端模块 | 分层规则由 `check:wiring` 强制 |
| 版本页文案不得含 markdown 标记 | 同上，有专门检查 |
| `nuxt dev` 在受限环境可能因 spawn 被拦 | 不是代码问题，别去"修"它 |
| 测试运行器需要 spawn 子进程 | 沙箱/受限环境下会失败，不是代码问题 |
